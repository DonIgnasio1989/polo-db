Расшифровка версии X.Y.Z
Часть	Что означает	Когда повышать	Пример
X (major)	Релиз — крупное обновление, ломающее совместимость	Смена формата базы, миграция IndexedDB, удаление функций, несовместимый экспорт JSON	1.0.0 → 2.0.0
Y (minor)	Фича — новые функции, обратная совместимость сохранена	Новый раздел, новый фильтр, новая модалка, новые данные без ломки формата	1.0.0 → 1.1.0
Z (patch)	Патч — исправления и мелочи	Фикс багов, правка артикулов, обновление каталога, косметика CSS	1.0.0 → 1.0.1

Правила:
    Ломающее изменение → X+1, а Y и Z обнуляются: 1.4.7 → 2.0.0
    Новая фича → Y+1, а Z обнуляется: 1.4.7 → 1.5.0
    Только фиксы → Z+1: 1.4.7 → 1.4.8
    Никогда не «откатывать» — только вверх

Суффиксы (опционально) для разработки:
    1.1.0-beta.1, 1.1.0-beta.2 — бета-сборки
    1.1.0-rc.1 — релиз-кандидат
    1.1.0 — стабильный релиз

Что менять в проекте
1. js/app.js — fallback-версия
Найди js:
let APP_VERSION = '19.2'; // fallback, если update.json не загрузится
Замени на:
let APP_VERSION = '1.0.0'; // fallback, если update.json не загрузится

2. data/update.json — уже правильно

{
  "appVersion": "1.0.0",
  ...
}

Оставляем.

3. Поля update.json — какие реально читаются
Реальный формат (с 1.8.x changelog — это МАССИВ записей, а не строка):
json

{
  "appVersion": "1.10.6",
  "releasedAt": "2026-10-24",
  "files": [ {"path": "data/parts.json", "type": "parts"}, ... ],
  "changelog": [ {"version": "1.10.6", "date": "2026-10-24", "changes": ["...", "..."]}, ... ]
}

Важно:
    appVersion  — читается лоадером index.html (кешбастинг js/app.js?v=…) и app.js;
    releasedAt  — читается app.js:3553 (дата в модалке «Обновление базы»).
                  Поля updatedAt НЕ существует — в старых заметках была опечатка;
    files[]     — если список непустой, грузятся ТОЛЬКО перечисленные файлы;
    changelog[] — version/date/changes; порядок строго по убыванию, без дублей
                  (проверяется tools/validate-data.js и tests/test_1106.js).
Пример эволюции (шпаргалка на будущее)
Событие	Было → Стало
Первый релиз	— → 1.0.0
Поправил опечатку в артикуле	1.0.0 → 1.0.1
Добавил поиск по донорам	1.0.1 → 1.1.0
Фикс мобильного меню	1.1.0 → 1.1.1
Ещё фиксы	1.1.1 → 1.1.2
Новый раздел «Кузовной ремонт»	1.1.2 → 1.2.0
Сменил схему ID деталей (старые бэкапы несовместимы)	1.2.0 → 2.0.0
Хотфикс к 2.0.0	2.0.0 → 2.0.1

Куда версия подставляется автоматически
В DOMContentLoaded уже есть:
js
['ver_gate', 'ver_footer', 'ver_about', 'ver_bug'].forEach(id => { ... });

Она подтянется во все места:
    гейт лицензии
    подвал сайдбара
    «О программе»
    заголовок баг-репорта

Единственное, что нужно — обновлять appVersion только в update.json, код трогать каждый релиз не придётся (кроме критичного fallback — но его можно менять раз в major).

Как выпускать релиз (чеклист)
    Внести изменения.
    Поднять appVersion в data/update.json по правилам выше.
    (Опционально) заполнить changelog.

    Если ломающие изменения — поднять DN/DV в app.js:
    js

    DN = 'vw_polo_v181', DV = 2;  // → 'vw_polo_v2', DV = 3

    Это сбросит IndexedDB у пользователей и заставит перекачать базу.
    Закоммитить, запушить. Приложение само подхватит новую версию.

Инструменты релиза (появились в 1.10.6)
    node tools/migrate-1.10.6.js     # разовая миграция data-src (идемпотентна)
    node tools/build-parts.js        # data-src → data/parts.json + parts.full.json + аналоги
    node tools/validate-data.js      # 8 блоков проверок, exit 1 на ошибках → restore/VALIDATION.md
    node tools/dedup.js --src data-src --out restore --apply
    node tests/test_1106.js          # 37 проверок релиза (без jsdom)

Порядок такой: миграция/правки data-src → build-parts.js (он сам прогоняет
валидатор до и после записи) → dedup.js → тесты → поднять версию в 5 местах.

Когда нужен «♻️ Пересобрать базу» у пользователей
    Ключ слияния в lAll() = oem + name. Новые записи прилетают сами, а вот
    УДАЛЁННЫЕ или ПЕРЕИМЕНОВАННЫЕ на сервере остаются в IndexedDB навсегда
    (пользователю нужно нажать «♻️ Пересобрать базу», а это стирает ручные
    цены/заметки/фото). Поэтому в 1.10.6 ничего не переименовывали: вместо
    этого поле sup («артикул заменён») и взаимные ссылки в инструкциях.

Когда поднимать DN/DV
    Только при смене СХЕМЫ данных. Правки содержимого (артикулы, применимость,
    инструкции) не требуют сброса — merge в lAll() перезапишет записи сам.
