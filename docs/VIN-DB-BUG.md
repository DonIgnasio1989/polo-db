# vin-db.json: поле `vin` не является VIN-кодом

**Дата диагноза:** 2026-10-24
**Основание:** фрагмент боевого `vin-db.json` (9 полных записей), присланный владельцем.
**Статус:** 🟢 первопричина найдена и исправлена (`tools/vin_extract.py`, версия vin_extract 1.1);
требуется пересборка `vin-db.json` на стороне владельца.
**Проверка:** `node tools/validate-data.js` — ловит этот случай автоматически (8 ошибок на 2 записях).

## Что именно сломано

Поле `vin` **собрано из последних пяти PR-кодов** этой же записи:

```
vin = <2 символа> + pr[-5] + pr[-4] + pr[-3] + pr[-2] + pr[-1]
```

Проверено на всех 9 присланных записях — **9 из 9 совпадений**:

| `vin` в файле | префикс | последние 5 кодов `pr` | склейка |
|---|---|---|---|
| `1ARLAT6VU2BV0AWV1` | `1A` | RLA T6V U2B V0A WV1 | ✓ |
| `1ARSYT6VSA7U2BV0A` | `1A` | RSY T6V SA7 U2B V0A | ✓ |
| `1ARSYT6VU1CV0AWV1` | `1A` | RSY T6V U1C V0A WV1 | ✓ |
| `1ARSYT6VU1DV0AWB1` | `1A` | RSY T6V U1D V0A WB1 | ✓ |
| `1DRLAT6VU2BV0AWS1` | `1D` | RLA T6V U2B V0A WS1 | ✓ |
| `1DRSYT6VU1CV0AWS1` | `1D` | RSY T6V U1C V0A WS1 | ✓ |
| `1DRSYT6VU2BV0AWS1` | `1D` | RSY T6V U2B V0A WS1 | ✓ |
| `1URBCT6NS8DU0CV0A` | `1U` | RBC T6N S8D U0C V0A | ✓ |
| `1URCHT6NS3YU0CV0A` | `1U` | RCH T6N S3Y U0C V0A | ✓ |

Такая строка формально проходит проверку «17 символов без I/O/Q», поэтому
внешне файл выглядит здоровым.

## Почему это не VIN

| Признак | Настоящий VIN из дампа | Присланный |
|---|---|---|
| WMI (1–3) | `WVW`, `WV1`, `WV2`, `VSS` | `1AR`, `1DR`, `1UR` — не VW/SEAT |
| filler (4–6) | `ZZZ` | `LAT`, `SYT`, `CHT`, `BCT` |
| код модели (7–8) | `6N`, `9K`, `9U` | `6V`/`6N` — **попал случайно**: это 2-й и 3-й символы PR-кода `T6V`/`T6N` |
| серийный номер (12–17) | 6 цифр (`530555`) | `V0AWV1`, `U0CV0A` — буквы |

## Каскад: что ещё стало мусором

`vD()` в `js/app.js` разбирает модель/год/завод **из строки VIN**, поэтому все
производные поля унаследовали ошибку:

| Поле | В присланных записях | Реальность |
|---|---|---|
| `year` | 1980, 2001, 2002, 2003, 2008 | берётся из 10-го символа псевдо-VIN; `prod_date` при этом 1994 и 2002 |
| `plant` | Bruxelles, Chattanooga, Bratislava, Pamplona | Bruxelles (Vilvoorde) закрыт в 1997; Chattanooga Polo не собирал; Bratislava — не Polo |
| `brand` | «Неизвестно» | WMI `1AR`/`1DR`/`1UR` не распознаётся |
| `body`, `gen` | «—», пусто | не определились из-за того же |
| `model` | «Polo Classic/Variant (6V)», «Polo (6N)» | совпало случайно — через PR-код `T6V`/`T6N`, попавший в 7–8 символы |

Генератор **сам заметил** часть проблемы: у 6 записей из 9 стоит
`"warn": "год VIN (2008) != год источника (1994)"`. На эти предупреждения
и надо было смотреть в первую очередь — это готовый индикатор поломки.

## Что в файле достоверно

* `pr` — 139 кодов у первой записи, **все 139 есть в `data/pr-codes.json`**;
* `paint` (`4B`, `3A`), `trim` (`20S4`, `20SH`, `20S5`, `50S4`, `53P5`, `56P5`);
* `prod_date` (`2002-02-28`, `1994-04-28` …) — согласуется с «годом источника» в `warn`;
* сам факт, что в этом прогоне **есть записи 6V (Polo Classic/Variant)**, которых
  нет в `vin-dump/filtered-vins.txt` (там 6V — ноль при заявленных 109 в meta).

То есть содержимое карточек ценное, потеряна только привязка к автомобилю.

## Последствия для приложения

1. `vinDbRow()` ищет точным совпадением `Map.get(vin.toUpperCase())` → ни один
   реальный VIN не найдётся, «📋 Оснащение (PR)» останется пустым для всех машин.
2. Если такой `vin-db.json` залить вместо `vin-db.filtered-only.json`, пропадёт
   даже распознавание «этот VIN есть в дампе» (13 359 настоящих VIN).
3. Автозаполнение мотора/КПП/краски/даты при добавлении VIN не сработает —
   в присланных записях нет ни `engine`, ни `gearbox`, ни `gearbox_code`.

## Первопричина ДОКАЗАНА

Владелец прислал генераторы — `tools/vin_extract.py` и `tools/make_vin_db_web.py`.
Виновник — **`vin_extract.py`**, связка из трёх мест:

1. **`VIN_RE`** — регулярка поиска VIN в тексте:
   `(?<![A-HJ-NPR-Z0-9])[A-HJ-NPR-Z0-9]{17}(?![A-HJ-NPR-Z0-9])`.
   В класс границ **не входят буквы I, O и Q** (их не бывает в VIN) — значит, `Q`
   внутри длинной строки считается **разделителем токена**.
2. **`iter_txt`** складывает строку из склеенных PR-кодов (417 символов без
   разделителей, `len % 3 == 0`) в поле `rec['pr']` одной строкой.
3. **`vin_candidates(rec)`** обходит **все строковые значения записи — включая
   `pr`** и ищет в них VIN этой регуляркой, а `build_record` принимает первого
   кандидата, который декодируется в модель каталога.

В PR-блобе `…PPA QH0 QA0 **Q**1A RLA T6V U2B V0A WV1` буква `Q` из кода `Q1A`
стала границей, и следующие за ней 17 символов — `1ARLAT6VU2BV0AWV1` — были
приняты за VIN. Проверка модели прошла случайно: символы 6–8 этой подстроки
попали на PR-код `T6V` → `6VU` → `startswith('6V')` → «наша модель».

**Прогон их же регулярки по восстановленному блобу:**

```text
PR-блоб: 139 кодов, 417 символов, len%3=0
хвост блоба: …8N4PPAQH0QA0Q1ARLAT6VU2BV0AWV1
VIN_RE.finditer(blob) → ['1ARLAT6VU2BV0AWV1']      ← «VIN» найден внутри PR-кодов
позиция в блобе: 400, символ перед ним: 'Q'
1ARLAT6VU2BV0AWV1: x[6:9]='6VU' → model_code=6V → matches()=True → принят
```

Отсюда же префиксы `1A` / `1D` / `1U` — это хвосты PR-кодов `Q1A` / `Q1D` / `Q1U`
(сама `Q` осталась за границей токена). А совпадение `vin[2:] == последние 5
PR-кодов` (9 из 9) — прямое следствие: «вин» вырезан из того же блоба.

## Что исправлено (`tools/vin_extract.py`, версия vin_extract 1.1)

| # | Правка | Зачем |
|---|---|---|
| 1 | `VIN_RE`: границы теперь `(?<![A-Z0-9])…(?![A-Z0-9])` | `I/O/Q` больше не разделители — подстрока внутри склейки PR-кодов не находится вовсе |
| 2 | `NO_VIN_SEARCH = ('pr','prcodes','prc','options','optioncodes','trim')` | второй рубеж: VIN не ищется в склейках кодов |
| 3 | Имя файла — **первый** кандидат (было последним) | дампы ETKA именуются настоящим VIN; раньше его перебивал мусор из содержимого |
| 4 | Новая `vin_is_real()`: серийная часть — **6 цифр**, WMI — из списка VW/SEAT/Audi/Skoda | отсекает 17-символьные внутренние ключи ETKA (FGST), «похожие на VIN» |
| 5 | `vin_soft_warn()` + счётчик `vin_filler_warn` | filler ≠ ZZZ виден в отчёте, а не молча уходит в базу |
| 6 | Год из источника (`year_src`) и `prod_date` **перекрывают** год из VIN | раньше в базу уходил 1980/2008 при `prod_date` 1994/2002 |
| 7 | Распознаётся VIN с разделителями (`WVW ZZZ 6V Z 2W 012345`, `WVW-ZZZ-…`) | такие записи раньше терялись целиком |
| 8 | В консоль и в `vin-db.meta.json` добавлены `rejected_not_vin`, `rejected_other_model`, `rejected_reasons`, `year_fixed_from_src` | видно, сколько кандидатов отсеяно и почему |

`make_vin_db_web.py` правок не требует: он просто переносит поле `vin` из
`vin-db.jsonl.gz` в `data/vin-db.json`.

## Важное следствие для вашей базы

Файлы, где **настоящего VIN нет ни в имени, ни в содержимом** (имя — внутренний
ключ ETKA), после правки **записей не дадут вовсе**. Это правильно: подделывать
VIN нельзя. Такой файл честно уходит в счётчик `FGST-ключи ETKA без VIN: N`.

Поэтому после пересборки смотрите на строку отчёта `FGST-ключи ETKA без VIN: N`:
если N велико — часть файлов именуется ключами, и их надо либо переименовать по
VIN, либо добавить настоящий VIN в содержимое (поле FGST-NR). Только тогда те
6V-машины, которых сейчас нет в `filtered-vins.txt`, вернутся в базу.

Порядок пересборки:

```
python3 tools/vin_extract.py -i "D:\etka-dump" -o ./out --include-donors -v
python3 tools/make_vin_db_web.py -i ./out/vin-db.jsonl.gz -o ../data
node tools/validate-data.js          # блок 8 «VIN sanity»: ошибок быть не должно
```

## Попутная находка: `pr-codes.json` пуст на 89 %

Из **1 723** кодов описания нет у **1 526** (89 %):

```
1E1 → "Activated carbon canister"          ← есть
3B0 → "Without additional child seat anchor"
RLA → ""                                    ← пусто
T6V → ""
WV1 → ""
```

Из 139 кодов присланной записи пустые описания у 69 % «основной» части и у 4 из 5
«хвостовых». Практический эффект: в модалке «📋 Оснащение (PR)» большинство строк
выглядит как «описание не найдено», а `pr-codes-ru.json` закрывает всего 122 кода
(7,1 %). Валидатор теперь сообщает об этом предупреждением.

⚠ **Важно:** «134 из 139 кодов найдено в словаре» — проверка **по кругу**,
словарь заполнялся флагом `--update-pr-dict` из этих же прогонов (новые коды
дописываются с пустым описанием). Доказывать корректность извлечения она не может.
Сами коды при этом настоящие (`3B0`, `6U0`, `2WA`, `4UE`, `7AA` — реальные PR),
так что задача остаётся контентной, а не программной.

План: взять коды, которые реально встречаются в `vin-db.json`, отсортировать по
частоте и заполнить описания начиная с самых частых (обычно первые 200 кодов
покрывают большую часть выдач).
